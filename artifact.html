Part I · Module 1

What Fullstory actually is

Almost every misconception a client has about Fullstory comes from thinking it records video. It does not. Understanding the capture model is what lets you answer the three questions every client asks in the first hour: is it slow, is it safe, and why can I not see that thing.

It is a DOM recorder, not a screen recorder

When the capture script initialises, it takes a structural snapshot of the page — the DOM tree, the computed styles, and references to the stylesheets and assets needed to draw it. From that moment on, it watches for changes using a MutationObserver and streams only the deltas: this node was added, this attribute changed, this text was replaced. Alongside that it streams an input event track — pointer position, clicks, scroll offsets, key events, viewport resizes, focus changes.

Playback reconstructs the page in an isolated iframe by replaying those mutations against the original snapshot, and draws a synthetic cursor from the input track. Nothing is rasterised at capture time. That single fact drives almost everything else:

Why the payload is small

A text diff is bytes; a video frame is kilobytes. Capture typically adds a low-single-digit percentage to page weight and the script loads asynchronously, so it should not block rendering. When a client says "we cannot add another tag, the site is heavy" this is your answer — but get the number from their own RUM rather than quoting a brochure figure.

Why you can inspect elements in replay

Because the page is real DOM, not pixels, you can open the element inspector mid-replay, read CSS selectors, and click through to console and network panels. This is the single biggest advantage over video-based tools and the demo moment that wins rooms.

Why some things do not replay

Anything drawn outside the DOM is invisible to a DOM recorder. That means <canvas> and WebGL render as blank, cross-origin iframes you do not control are not captured, video elements show as a box, and Shadow DOM needs explicit support. For casino clients this is the headline caveat: the slot game itself will not replay. See the module on lobby and game instrumentation for how to work around it.

Why replay can look "wrong"

Playback fetches CSS and images from their live URLs at the time you watch. If a stylesheet has since been redeployed, or an asset sits behind auth or a short-lived CDN signature, the replay renders with the new styling or with gaps. Fullstory mitigates this by capturing stylesheet contents where it can, but on heavily personalised or aggressively cache-busted sites expect some drift, and expect a client to point at it.

The unit hierarchy

Event
The atom. A click, a page navigation, a console error, a custom event you fired. Everything searchable is an event or a property on one.
Page view
A logical page within a session. On a single-page app this is not automatic — you must tell Fullstory when a virtual page change happens, or your whole sportsbook looks like one enormous page.
Session
A contiguous run of activity from one browser. It ends after 30 minutes of inactivity, or 24 hours of active capture, whichever comes first. A player who deposits in the morning and bets in the evening is two sessions. Within a session, a stretch counts as inactive once four seconds have passed since the last user action — that four-second threshold is what the player's "skip inactivity" control collapses.
User
A stable identity across sessions and devices, keyed by the uid you supply. Without setIdentity you get a per-device cookie identity that cannot be joined to anything in the client's warehouse — which makes most gambling analysis impossible.
Segment
A saved, re-evaluating definition of a set of sessions or users. The workhorse object: funnels, dashboards, metrics and replay lists all hang off segments.

Where the data goes

Captured deltas are batched and posted to Fullstory's ingest endpoints, processed, indexed, and made available for search and replay within minutes — not instantly, which matters when a client is watching you demo a fix live. Retention is a contractual setting, commonly somewhere between one and thirteen months by plan; anything the client needs beyond retention must be exported to their warehouse before it ages out.

Data residency matters enormously for your clients. Operators licensed in the UK, Malta or Ontario will have a regulator-facing answer to "where is player data stored" and your Fullstory configuration has to be consistent with it. Establish the client's residency requirement in discovery, not in week six.

Say this

"Fullstory does not record your screen. It records the structure of your page and the changes to it, then rebuilds the page on playback. That is why it is light, why we can inspect elements and read your console errors inside a replay, and why your game canvases will show as blank — which we will instrument around."

Part I · Module 2

Getting it on the site — properly

Deployment is where most gaming accounts quietly fail. Not because the snippet is hard, but because a typical operator has three brands, two front ends, a white-label platform they do not control, a native app team who were not in the meeting, and a consent management platform that blocks the tag by default.

The four ways in

1. Direct snippet best

Paste the capture snippet high in <head>, before other tags where possible. Earliest initialisation means you capture the pre-render state and the errors that happen during boot. Requires a release from the client's dev team.

2. npm package

@fullstory/browser for SPAs. Gives typed helpers, a clean init call in your app bootstrap, and version control. Preferred by any operator with a modern React or Vue front end.

3. Google Tag Manager compromise

Fast to deploy and the usual answer when dev capacity is zero. Costs you: later initialisation (you miss early errors), dependence on GTM's own load, and a consent layer that frequently suppresses the tag. Acceptable for a proof of value, not for the long term.

4. CDP / tag platform

Segment, mParticle or Tealium can carry Fullstory as a destination. Attractive when the client already routes identity through a CDP, because identity and events arrive consistently. Watch for the CDP stripping or renaming properties in transit.

The snippet, annotated

window['_fs_host'] = 'fullstory.com';
window['_fs_script'] = 'edge.fullstory.com/s/fs.js';
window['_fs_org'] = 'YOUR_ORG_ID';

Namespace collisions: some gambling platforms already define a global FS; if so, set _fs_namespace to something unique like FSB and make sure every downstream call uses it. Single-page apps: the page-view problem

A sportsbook built as an SPA will, by default, look to Fullstory like a single page that lasts forty minutes. Funnels break, page-level metrics are meaningless, and heatmaps blend six screens together. You must signal virtual page changes on every route transition.

// Browser API v2 — call on every route change
FS('setProperties', {
  type: 'page',
  properties: {
    pageName: 'Casino Lobby',
    lobbyCategory: 'Slots',
    gameCount: 412
  }
});

Attach the router hook, not a manual call per component — a manual call always drifts. In React Router, Vue Router or Next's router events, one central subscriber is the correct pattern.

Gaming

White-label platforms. A large share of mid-market casino brands run on someone else's platform — the operator owns marketing and the brand skin, the provider owns the cashier, the game launcher and often the registration flow. You will be told "we can add tags" and discover that means the marketing pages only. Establish in discovery which pages the client can deploy code to and get it in writing. Where the platform provider controls the cashier, your options are: (a) the provider adds the snippet under their own contract, (b) same-origin iframe capture if the cashier is served from the operator's domain, or (c) you instrument up to the cashier boundary and treat the drop as a black box you measure the edges of.

First-party capture

Ad blockers, browser tracking protection and some corporate networks block third-party analytics hosts. In gambling this bites harder than average — the audience skews toward privacy tooling, and blocked capture silently biases your entire dataset toward less technical users. Fullstory supports serving capture through a first-party subdomain (for example fs.brand.com via a CNAME or reverse proxy). It requires DNS and infrastructure work from the client, so raise it early, but on a gambling account it is usually worth the fight. Quantify it first: compare Fullstory session counts against the client's own server-side page-view counts and show them the gap.

Native apps

Fullstory has mobile SDKs for iOS, Android, React Native and Flutter. Three differences from web that you must communicate:

  • Privacy defaults invert. On web, inputs are private by default and you opt elements out. On mobile the SDK generally captures the view hierarchy and you must explicitly mask sensitive views. Assume nothing is masked until you have proved it in a replay.
  • Release cadence gates you. Every instrumentation change ships with an app release and waits for store review and user adoption. Plan mobile event schemas properly the first time; you do not get to iterate weekly.
  • Webviews. Most gambling apps are partially webviews — the cashier and the game launcher especially. You need the web capture script inside the webview and the native SDK, correctly linked, or the session fractures at the most important moment.

Deployment checklist

  1. Environment inventory List every domain, subdomain, brand skin, locale variant and app. Gambling groups routinely run brand.com, brand.de, m.brand.com and a separate poker client.
  2. Deploy to staging first Verify capture, then verify masking. Never let the first production session be the first time anyone looks.
  3. CSP and consent Confirm the tag fires post-consent in every consent state, and that it does not fire pre-consent in markets that require it.
  4. Identity wiring Confirm setIdentity fires on login and on session restore, with the hashed player ID that matches the warehouse key.
  5. SPA page rules Confirm each route produces a distinct, human-readable page name.
  6. Privacy audit Walk registration, KYC upload and the cashier in a real session, then watch the replay and confirm every sensitive field is masked. Screenshot it for the compliance file.
  7. Volume sanity check Compare session counts to the client's analytics for the same window. A gap over roughly 10–15% means blocking, consent suppression or a missing deployment surface.

Identity — the join that makes everything else possible

Anonymous session replay is a curiosity. Identified session replay joined to the client's revenue data is a business case. In gambling, the identity decision is also the one most likely to get you in front of a Data Protection Officer, so get it right and get it documented.

The call

FS('setIdentity', {
  uid: 'a3f9c21e8b',                 // hashed/pseudonymous player ID
  properties: {
    displayName: 'Player a3f9c21e8b', // never the real name
    // reserved: email — OMIT for gambling clients
    accountTier: 'Gold',
    registrationDate: '2024-11-02T00:00:00Z',
    kycStatus: 'verified',
    marketCode: 'UK',
    brand: 'BrandA',
    depositCountBucket: '6-20',
    isVip: false,
    selfExcluded: false
  }
});

Rules for the uid

  • It must be stable. Same player, same uid, forever, across devices and brands where the client's account model allows it.
  • It must be joinable. The uid has to be a key the client's warehouse already holds, or the whole point — joining behaviour to GGR — evaporates. Agree the key with the BI lead, not the front-end developer.
  • It must be pseudonymous. Never the email, never the username, never the account number if that number appears on statements or is quoted to customer service. A salted hash of the internal player ID, computed server-side, with the salt held by the client. Under UK GDPR this keeps the data pseudonymous rather than directly identifying, which materially changes the client's risk assessment.
  • It must be reversible by the client only. The client keeps the lookup table so they can honour a subject access or erasure request. You should not hold it.
One shot

Identity is immutable. Once a session has been assigned a uid through setIdentity, Fullstory does not let you change that user's identity afterwards. There is no correcting a mistake later, and no re-keying a population once you discover the hash was built wrong. This is why the identity design is a Phase 2 decision signed off by the BI lead, not something a front-end developer picks in a ticket — get the key wrong and you are re-instrumenting from a clean start, having lost the history.

Do not

Do not populate the reserved email property on a gambling account, and push back hard if asked. It is directly identifying, it lands in a third-party system, it creates a marketing-consent question nobody wants to answer, and the analytical value is zero — you can do everything you need with a hashed uid. The one legitimate exception is a client whose DPO has explicitly signed it off in writing for a support-lookup use case; even then, prefer a reference number.

Anonymous-to-identified stitching

A player lands from an affiliate link, browses the lobby, reads the promotions page, then logs in. The pre-login activity is anonymous; the post-login activity is identified. When setIdentity fires, Fullstory attaches the current session to that user. The sessions before that one, on the same device, generally remain anonymous — which is exactly the acquisition window your client cares most about.

Two mitigations worth knowing:

  • Identify as early as legitimately possible. If a returning player's session is restored from a persistent cookie before they re-authenticate, call setIdentity at that point rather than waiting for an explicit login.
  • For acquisition analysis, accept anonymity and instead capture the campaign context as page/session properties — affiliate ID, campaign, landing variant — so you can analyse the anonymous funnel on its own terms and join at the aggregate level.

Consent-aware identity

In markets that require prior consent, the correct pattern is to start capture manually and identify only after consent is recorded.

// init with startCaptureManually: true, then on consent:
if (consent.analytics === true) {
  FS('start');
  FS('setIdentity', { uid: hashedPlayerId, properties: { /* ... */ } });
}

// on consent withdrawal
FS('shutdown');           // stops capture for this session
// and trigger a deletion request server-side for that uid

Withdrawal is not just switching capture off. The client has an obligation to delete already-captured data on request, which is done through the server-side API — covered in the Data Direct and API module. Make sure someone at the client owns that runbook; do not let it be you by default.

Autocapture, custom events, and the schema you will live with

Fullstory's strongest claim is retroactive analysis: because it indexes every interaction automatically, you can ask a question today about behaviour from last month that nobody thought to tag. That is true, and it is also where teams get lazy. Autocapture answers "what did they click"; only a designed schema answers "what did that cost us".

What you get for free

Out of the box, with no tagging, Fullstory indexes: every click and tap with the element's text, selector and position; every page navigation; scroll depth and reading behaviour; form field interactions (which field, focus order, time in field, abandonment — not the values, which are private by default); console messages and JavaScript errors with stack traces; network request timing and failures; page performance timings; and the derived frustration signals covered in their own module.

The practical consequence: you can run a genuinely useful first workshop on day one of capture, before a single line of custom instrumentation exists. Use it. Nothing builds client belief like finding a real problem in week one.

The five rules of a schema that survives

  1. Name events for what happened, not for where the code is Deposit Completed, not cashier_step3_success_v2. Business users search this list. If they cannot read it, they will not use the tool, and your adoption metric dies.
  2. Fix a naming convention on day one and write it down Title Case for event names, camelCase for properties, is the convention this platform uses throughout. Any convention works; inconsistency does not. Put it in the instrumentation spec and make the client's tech lead sign it.
  3. Bucket high-cardinality values Raw stake amounts, raw deposit amounts and raw odds create unusable segment dropdowns and make aggregation meaningless. Send stakeBucket: "10-24.99" as the segmentable property, and keep the raw figure only if there is a genuine need — and never if it is not needed for the analysis.
  4. Never send anything you would not want in a subject access response Assume every property will one day be printed and handed to a player or a regulator. No names, no emails, no card fragments, no document numbers, no free-text the player typed.
  5. Carry a join key Every commercially significant event should carry an ID the warehouse also holds — depositId, betId, sessionRef. This is what turns "18% of players who saw the error churned" into "that error cost £340k of NGR".

Element identification

Autocapture identifies elements by selector and text, which is fragile on sites that ship CSS-in-JS hashed class names or that localise button copy. Give important elements a stable identifier:

<button data-fs-element="Cashier / Deposit Confirm">
  Deposit £50
</button>

Now the element is findable as "Cashier / Deposit Confirm" in every locale and after every rebuild. On a multi-language operator this is not a nicety; without it your German funnel and your English funnel are different funnels. Agree a naming scheme — Area / Component / Action reads well and sorts well.

Privacy, masking and the compliance conversation

On a gambling account this is not a module, it is a gate. You will not get a snippet into production until the Data Protection Officer is satisfied, and the fastest route through is to arrive already knowing more about the controls than they expect you to.

Private by default

Fullstory's web capture treats user input as private by default: the values typed into inputs, textareas and select elements are not captured, while the interaction (focus, blur, time in field, whether it was completed, validation errors shown) is. This is the right default and it is your opening line with a DPO: "We do not capture what players type unless someone explicitly opts a field in, and on your site nothing will be opted in."

Element text that is rendered on the page — a displayed balance, a name in the account header, a bet history table — is captured unless you exclude or mask it. That is where the real work is.

The three levels of suppression

Two traps

1. Excluding an element throws away its clicks. Events that target an excluded element — clicks and changes — are ignored entirely. Put fs-exclude on the deposit confirm button and you lose the fact that anyone pressed it, which silently breaks your deposit funnel. Exclude the card fields, never the surrounding controls. Masking is the right tool whenever you still need the interaction.

2. Masked text cannot be searched by text. Because the actual strings are never collected, you cannot find a masked element by its copy — you must search by CSS selector. This is the strongest practical argument for naming your important elements with data-fs-element before you mask anything around them.

There are also consent variants of these classes, which apply only until consent is recorded — useful in markets where you capture a reduced dataset pre-consent. And where an element matches both a masking and an unmasking rule, the stricter rule wins; to unmask inside something stricter you have to create an explicit exception rather than relying on ordering.

<!-- never leaves the browser -->
<div class="fs-exclude" id="card-entry"> ... </div>

<!-- shape kept, content obfuscated -->
<span class="fs-mask" data-balance>£1,284.50</span>

<!-- opt a child back in -->
<div class="fs-mask">
  <p class="fs-unmask">Verification failed: document expired</p>
</div>

There are also UI-side rules: in Fullstory's privacy settings an admin can define selector-based blocking and masking that applies without a code change. Use these as a safety net and for emergencies, never as the primary mechanism — rules defined in the UI are invisible to the client's developers and will be broken by the next redesign without anyone noticing. This is not just a preference: Fullstory's own documentation recommends the code-first approach, on the grounds that classes in the component library are less brittle and more future-proof than CSS selectors maintained in a settings screen. Quote that when a client's developer resists taking the ticket.

Fullstory also publishes a Privacy Setup Checklist and documents the Private by Default behaviour. Work through the checklist with the client's DPO in the room rather than presenting your own; using the vendor's own artefact shortens the argument considerably.

Critical

Masking rules apply at capture time and are not retrospective. If a field was captured unmasked for three weeks, adding fs-exclude today does not clean the history — that requires deletion via the API or a retention purge. This is the sentence that will one day save you: test masking in staging, and audit it in production within 24 hours of go-live.

The special-category question

Gambling behaviour is not formally special-category data under UK/EU GDPR in the way health data is. But responsible-gambling status is adjacent to health — an operator's markers-of-harm model, a self-exclusion flag, or an intervention record can reasonably be argued to reveal information about a person's mental health or addiction. Treat it as if it were special category:

  • Never send a markers-of-harm score, risk band, or intervention history into Fullstory as a user property.
  • You may capture that an RG tool was used — that a deposit limit screen was opened, that a reality check was dismissed — because that is interaction data and it is precisely what the client needs to improve RG journeys. Keep it at the interaction level, not the diagnosis level.
  • Never build a segment whose purpose is to target at-risk players commercially. If a client asks for one, say no, and say why. This is a licence-condition issue for them and a reputational one for your firm.

Consent management

Most operators run a CMP (OneTrust, Cookiebot, Didomi, Sourcepoint). Capture belongs in the analytics or performance category, and must respect the player's choice. The implementation pattern is the one shown in the identity module: startCaptureManually, then FS('start') on consent, FS('shutdown') on withdrawal.

Two things clients get wrong. First, they gate the tag but not the identity call, so a rejected-consent user still gets identified by a race condition. Second, they never test the withdrawal path. Both are five-minute checks in a replay; do them.

Retention, deletion and access

Retention
Set per contract. Shorter retention is easier to defend to a regulator and cheaper; longer retention lets you analyse seasonality and annual events. For most operators 3–6 months of replay with warehouse export for anything longer is the defensible compromise.
Right to erasure
Handled by a server-side API call that deletes a user by uid. The client needs a documented runbook connecting their DSAR process to that call, with an owner and an SLA. Build it during onboarding; it is a two-hour job that prevents a genuine crisis.
Right of access
A player can ask what has been captured. The honest answer is a list of interaction events and a description of the replay; be ready to help the client word it.
Processor role
Fullstory is a data processor; the operator is the controller. There will be a DPA, and there may be standard contractual clauses depending on residency. You do not sign these — but knowing the vocabulary keeps the meeting moving.
Access control
Not everyone at the client should see replay. Restrict replay access to a named group, keep dashboards open to everyone, and log it. "Who can watch a player's session" is a question a regulator may genuinely ask.
Deliverable

Produce a one-page Data Capture Statement for every client: what is captured, what is excluded, what is masked, retention period, who has access, deletion runbook, and the date of the last masking audit. It takes an hour, it closes the DPO conversation permanently, and it is the single most reused artefact you will build.

Part I · Module 6

Replay, used properly

Anyone can press play. The skill is knowing which twenty sessions out of eleven million to watch, what to look for, and how to turn twelve minutes of watching into a sentence an executive acts on.

The player surface

  • Event timeline down the side: every click, navigation, error and custom event. Click any entry to jump. This is how you skip to the moment that matters instead of scrubbing.
  • Skip inactivity on by default — be aware, because a client watching a "fast" session may not realise there was a 40-second wait that was compressed. When you are demonstrating a slow experience, turn it off.
  • Console tab — the JavaScript errors and logs from that session, in time order with the replay. This is the feature that converts developers.
  • Network tab — request timing and failures. Where you prove that the deposit spinner span eleven seconds because the PSP call hung.
  • Element inspector — hover and read the actual selector of what the player clicked.
  • Sharing — a link to a session at a timestamp. Respect access rules; do not paste player sessions into open Slack channels.

How to actually find the right session

Never browse the session list. Always arrive at replay from a question. The disciplined path is: metric moved → segment that isolates it → funnel step where it breaks → the sessions that failed at that step → watch five.

  1. Start from the anomaly "Deposit success on Apple Pay fell from 94% to 81% on Tuesday." Build the segment: deposit attempted, method Apple Pay, outcome failed, last 7 days.
  2. Sort for signal, not recency Prefer sessions that also contain an error click or a JS error, or that ended in a support contact. Those sessions carry the causal chain.
  3. Watch five, not fifty Five sessions from a tight segment almost always reveal the pattern. If five do not, your segment is too loose — go back and tighten it rather than watching more.
  4. Watch for the pause The moment of truth is nearly always a hesitation: cursor stops, the player rereads, they scroll back up. That is where comprehension broke.
  5. Confirm at scale before you claim it One replay is a hypothesis. Turn the pattern into a segment, count it, express it as a rate and an absolute number of players per month. Only then does it go in a deck.
Discipline

The single most common failure of a new Fullstory account is replay tourism — the client watches sessions, finds something interesting, and mistakes an anecdote for evidence. Your job from week one is to model the opposite: every replay observation you present is paired with a number. "I saw it happen" is worthless; "I saw it happen, and it happens to 4,100 players a month, 38% of whom never deposit again" is a roadmap item.

Gaming-specific replay realities

The game is a black box

Slots, live dealer and most sportsbook in-play widgets render in canvas or a third-party iframe. Replay will show a blank rectangle. You instrument the edges: launch requested, load succeeded or failed, time to playable, exit, and the return-to-lobby state. That is where the UX problems actually live anyway — almost no losses happen inside the game, they happen getting into it and getting money in.

Sessions are long and bursty

A casino session can run for hours with long idle periods. Use event-timeline jumps rather than scrubbing, and be careful quoting "average session duration" to a client — in gambling it correlates with spend but it is also the metric most contaminated by idle tabs.

Balance is masked, so infer

You will not see the player's balance. Infer state from behaviour: repeated cashier opens, a deposit attempt immediately after a game exit, stake-size changes. Instrument a balanceBucket property if the client will allow it — it is a powerful segmentation dimension and it is not directly identifying.

Multi-tab play is normal

Serious players run several games at once, sometimes across tabs. Fullstory captures each tab; sessions can look fragmentary. Do not interpret a "half-finished" journey as abandonment without checking whether the player continued in another tab.

Playlists and the deliverable

Fullstory lets you collect sessions into a saved list. Use it as your delivery format, not as a scrapbook. A good playlist has: a title that states the finding, three to five sessions that each show the same failure, and a written note per session saying what to watch for and at what timestamp. Hand that to a product owner and the ticket writes itself.

For executives, do not hand over replays at all. Hand over a single clip or screenshot sequence embedded in the number. Senior stakeholders in gambling companies are extremely time-poor and will not open a link.

Segments — the object everything else is built from

Funnels, dashboards, metrics, alerts and replay lists are all downstream of a segment. Learn to build them precisely and the rest of the product becomes easy. Build them sloppily and every number you produce afterwards is wrong in a way nobody will catch.

Session scope versus user scope

The distinction that trips up every new user. A session segment answers "which visits had this shape". A user segment answers "which people have ever done this". They give different numbers and they answer different questions.

The operators you will use constantly

Both the analysis window and relative windows within a session. "Within 60 seconds of" is how you tie a technical failure to a behavioural consequence.

Part I · Module 8

Quantifying it: funnels, journeys, metrics and dashboards

This is where you move from "here is a video of a problem" to "here is the number, here is what it costs, here is what happens if we fix it". Everything in this module is what makes the tool survive a budget review.

Funnels

A funnel is an ordered sequence of steps, each defined as an event or page view, evaluated per user or per session over a window. Fullstory computes step-to-step conversion, drop-off, and time between steps, and — the important part — lets you jump straight into the replays of the people who dropped.

The four funnels every gambling client needs

Acquisition to first deposit

Landing → Registration Started → Registration Completed → KYC Passed → Cashier Opened → Deposit Attempted → Deposit Success. Seven steps, usually 2–6% end-to-end from landing. This funnel is the client's entire acquisition economics in one picture.

Deposit (returning player)

Cashier Opened → Method Selected → Deposit Attempted → Deposit Success. Short, high-volume, and the highest-leverage thing you will ever optimise for these clients. A point of deposit success rate is worth more than most redesigns.

Game engagement (casino)

Lobby Viewed → Game Tile Clicked → Game Launched → Game Load Success → First Spin. The drop between launch and load success is a technical KPI you can hand to the provider-management team with real leverage.

Betslip (sportsbook)

Event Viewed → Selection Added → Stake Entered → Bet Placed → Bet Accepted. The gap between Placed and Accepted is price-change rejection — a metric most sportsbooks under-measure and one that quietly destroys in-play conversion.

Rigour

Always overlay a segment on a funnel before you present it. An aggregate deposit funnel across a multi-brand, multi-market operator is close to meaningless — the German funnel has a deposit limit step the UK one does not, and mobile web behaves nothing like the app. Segment by market, then device, then new versus returning. If the client only lets you show one cut, show new players on mobile web: it is usually the worst and the biggest.

Journeys

Where a funnel tests a hypothesis you already have, a journey (path analysis) shows you what actually happens — the most common forward paths from a starting point, or backward paths into an endpoint. Two uses that repay the effort:

  • Backwards from a bad outcome. Set the endpoint to Support Contact Initiated or Withdrawal Requested and look at what precedes it. You will find loops nobody knew existed.
  • Forwards from the lobby. For casino clients, what does a new player actually do after landing in the lobby? Almost always a great deal of aimless scrolling before any game launch, which is a merchandising finding, not a UX one — and it is worth a lot of money.

Metrics, dashboards and alerts

A metric is a saved, charted count or rate — typically "sessions matching segment X" or "conversion of funnel Y" over time. Dashboards assemble them. Alerts fire when a metric moves beyond a threshold or deviates from its expected pattern.

Dashboard design that survives contact with an executive

  1. One dashboard per audience, not per feature An Exec dashboard, a Product dashboard, an Engineering dashboard, a Payments dashboard. The same metric can appear on several; nobody should have to scroll past someone else's numbers.
  2. Rates above counts Counts move with traffic and seasonality — and gambling traffic is violently seasonal around fixtures and jackpots. A rate is interpretable on a Monday morning; a count is not.
  3. Always show the denominator "Deposit success 91%" means nothing without "of 42,000 attempts". Gambling stakeholders are numerate and will lose confidence in any chart that hides its base.
  4. Annotate releases Get the client to mark deploys and campaign launches. Half of all dashboard questions are "what happened on the 14th" and the answer is almost always a release.
  5. Cap it at eight tiles Anything more and it is a report, not a dashboard, and will be ignored.

How to read them without embarrassing yourself

Rage clicks are not all rage

Rapid clicking is also how people interact with steppers, quick-stake buttons, "+£10" chips and spin buttons. A sportsbook's stake stepper will generate enormous rage-click volume that means nothing. Always exclude known repeat-click controls — Fullstory supports suppressing the signal on specific elements, and if you do not do this your top rage-click element will be the spin button and your first report will be laughed at.

Dead clicks include the harmless

Clicking on whitespace, on a heading, on an image — people click things. The signal matters when it clusters on an element that looks like a control. Filter to elements with button-like or link-like styling before you report anything.

Error clicks are the gold

Of all the signals, error clicks have the highest ratio of genuine, fixable, revenue-affecting defects. Start every new engagement here: sort error clicks by affected sessions, take the top five, quantify the downstream conversion loss for each, and hand engineering a ranked list. This is the exercise that most reliably produces a win inside two weeks.

Frustration is a rate, not a count

Report frustration as a percentage of sessions on that page, trended, segmented by device. Raw counts just tell you which page has the most traffic — which will be the lobby, every time, and tells you nothing.

Turning a signal into money

The method, which you should be able to run without notes:

  1. Isolate Segment: sessions containing signal S on element E.
  2. Size it How many sessions and how many distinct players per month.
  3. Find the counterfactual Build the matched segment of sessions that reached the same step without the signal.
  4. Measure the delta Compare the downstream conversion rate — deposit success, bet placed, next-day return. The gap is your effect size. Be honest that it is correlational, and say so before someone else does.
  5. Price it Multiply the delta by affected players and by the client's own value figure — ARPU, average first deposit, or NGR per active. Always use the client's number, never your own. The moment you use their finance team's figure, the finding becomes their finding.
  6. Bound it Present a range, not a point. "Between £180k and £340k of annualised NGR, depending on whether the effect is causal" is credible. A single confident number invites an argument about the number instead of a decision about the fix.
Positioning

This calculation is the core of what a conversion consultancy sells. Fullstory is the instrument; the quantified, prioritised, defensible opportunity list is the product. Teach the client to run step 1 to 3 themselves — and keep steps 4 to 6 as the thing they keep paying you for.

Getting data out and joining it to money

The in-product UI is where analysis happens. The export layer is where Fullstory stops being a UX tool and becomes part of the client's data estate — and it is the difference between a renewal conversation about seat count and one about strategic value.

Anywhere: Warehouse — the warehouse sync

naming This capability has been called Data Direct and Data Destinations. Current branding is Fullstory Anywhere: Warehouse. Expect all three names in client conversations and older decks.

It delivers Fullstory's captured event data into the client's own warehouse on a managed, roughly hourly sync. Supported warehouse destinations are Snowflake, Google BigQuery and Amazon Redshift; raw event data can also be dropped into cloud storage — Amazon S3, Google Cloud Storage or Azure Blob Storage — without you building an ETL pipeline. Two shapes are available: Ready to Analyze Views, which are pre-transformed and are what an analyst should start from, and Raw Data, for teams who want to model it themselves. Once it lands, the client's analysts can join it to everything they already have.

That join is the whole point. On its own Fullstory knows a player rage-clicked the cashier. The warehouse knows that player's lifetime deposits, their NGR, their bonus cost and whether they churned. Together:

-- the query that justifies the contract
SELECT
  fs.error_signature,
  COUNT(DISTINCT fs.uid)                    AS players_affected,
  AVG(p.ngr_next_30d)                          AS avg_ngr_affected,
  AVG(c.ngr_next_30d)                          AS avg_ngr_control,
  AVG(c.ngr_next_30d) - AVG(p.ngr_next_30d)   AS ngr_gap_per_player
FROM fullstory_events fs
JOIN player_value p  ON p.player_hash = fs.uid
JOIN matched_control c ON c.cohort_key = p.cohort_key
WHERE fs.event_name = 'Deposit Outcome'
  AND fs.outcome     = 'failed'
GROUP BY 1
ORDER BY ngr_gap_per_player DESC;

You will not usually write this yourself — the client's BI team will. Your job is to make sure the uid is joinable, the event schema is stable, and the BI lead is in the room from week one. A Data Direct pipeline built without the BI lead's involvement is a pipeline nobody queries.

The server-side APIs

Users API
Read, update and delete users by uid. The delete endpoint is what backs the client's erasure runbook. Also useful for enriching user properties server-side with attributes the browser should never see.
Events API
Send events from your servers rather than the browser. Essential in gambling: deposit settlement, withdrawal approval, KYC outcome and bonus grants all happen server-side and often minutes later. Server events are also tamper-resistant, which matters if anything you measure touches a regulated process.
Sessions / Export API
Retrieve session metadata and replay links programmatically — how you attach a replay link to a support ticket automatically.
Segments API
Read segment membership programmatically, for feeding a CRM suppression list or triggering a workflow.
High value

The browser cannot reliably know whether a deposit truly settled — it only knows what the page showed. For any gambling client, push the authoritative outcome from the server via the Events API and keep the browser event as the client-side view. When the two disagree, you have found something genuinely valuable: the player was told one thing and the system did another. That discrepancy is a complaint, a chargeback, or a regulatory issue waiting to happen, and no other tool in their stack will surface it.

Gambling-specific and underrated. Feed a Fullstory segment ("failed first deposit in last 24h") into the CRM as a trigger audience. The client's retention team suddenly has a behavioural trigger they could not build before.

Multi-brand and multi-market structure

Four viable patterns, and the choice is consequential.

One org, brand as a property usually right

All brands in one workspace, distinguished by a brand user and session property. Cross-brand analysis is trivial, licences are pooled, segments are shared. Requires discipline: every segment must filter by brand or the numbers are nonsense.

Umbrella over separate accounts multi-brand groups

Fullstory supports an Umbrella structure: several distinct accounts governed together, with an Umbrella Manager able to administer users across all of them. This is the pattern purpose-built for a gambling group that needs per-brand separation without losing central administration. Ask about it by name — most clients do not know it exists.

Separate orgs per brand

Hard isolation with no shared administration. Necessary when brands are legally separate entities, when a regulator requires data segregation, or when one brand is a joint venture. Costs you cross-brand analysis entirely and multiplies admin work.

Split by regulatory region

One org per data-residency regime. Often forced by law rather than chosen. Plan for the reporting overhead — someone will have to combine numbers manually, and it should not be you every month.

Session quotas and sampling

Fullstory contracts are typically bounded by captured sessions. High-traffic gambling sites can burn a quota fast, especially around a major fixture or a jackpot. Three levers, in order of preference:

  1. Exclude worthless traffic first Bots, uptime monitors, internal IP ranges, the affiliate-testing traffic that hits the homepage and leaves. This is free quota and usually recovers 5–15%.
  2. Sample low-value surfaces Capture 100% of cashier, registration and KYC; sample the marketing and content pages. Never sample the money flows — the whole point is that rare failures are the expensive ones, and sampling hides exactly those.
  3. Sample by user, not by session If you must sample broadly, sample consistently per user so that a given player's journey is either fully captured or not at all. Sampling per session gives you fragmentary journeys that are worse than no data because they look complete.
Watch

Set a quota-burn alert at 60% and 80% of the contracted period's allowance. Running out of sessions three weeks before renewal, during the Grand National, is a genuinely account-threatening event — and it will be attributed to you regardless of who configured it.

SSO, provisioning and hygiene

  • SAML SSO for anything beyond a handful of users; gambling operators have mature identity infrastructure and will expect it.
  • SCIM provisioning where available so leavers lose access automatically. In an industry with high staff turnover this matters more than usual.
  • Quarterly access review. Who can watch replays should be a short, current list. Volunteer this review; it builds enormous trust with a compliance function.
  • A naming and ownership convention for segments, funnels and dashboards, with an owner recorded on each. Abandoned analytics objects are how an account quietly dies.

The structural difference that matters most

"You cannot change the maths of the game, and you would not want to. But you can change how many people get to it with money in their account, and how many of them come back. That is where I work."

Where sportsbook and casino players differ behaviourally

Sportsbook

  • Demand is event-driven and spiky — the Grand National, a derby, a title fight. Traffic can go up tenfold in an hour.
  • Extreme time pressure in-play. A two-second delay is a lost bet, not a mild annoyance.
  • Deep navigation: sport → competition → event → market → selection. Lots of places to lose people.
  • Multiples and accumulators are hugely profitable and disproportionately mobile.
  • Price changes between selection and placement cause rejections that players experience as the site "cheating" them.

Casino

  • Demand is steadier, with evening and late-night peaks and a strong weekend pattern.
  • Discovery is the core problem: hundreds or thousands of games, most of which are never launched.
  • Sessions are long, repetitive and often multi-tab.
  • Bonus mechanics (wagering requirements, game weighting, max bet rules) are the biggest source of confusion and complaint.
  • Game load performance is a direct revenue lever and is usually owned by a third party.

Cross-sell: the thing every group wants and few do well

Almost every large operator runs sportsbook and casino under one wallet and wants sportsbook customers to play casino, because casino NGR per active is typically much higher and far less volatile. The usual implementation is a banner, it usually fails, and it is a reliable early win for you: instrument the cross-sell surfaces, measure click-through and the resulting first casino session, and you will almost always find the banner is being ignored while an in-betslip or post-settlement placement performs several times better.

Stakes minus player winnings. The operator's gross take before any costs. GGR = Handle − Payouts
NGR
Net Gaming Revenue
GGR minus bonus cost, gaming duty, payment processing fees and often affiliate commission. This is the number that matters. When you price an opportunity, price it in NGR or you will be corrected in the meeting.
Hold % / Win %
Sportsbook. GGR ÷ Handle. Typically around 5–10% depending on mix; higher on multiples, lower on single-outcome markets and in-play.
Margin / Overround / Vig
The theoretical edge built into the prices on a market. A book priced to 105% has a 5% overround. Theoretical; hold is what actually happened.
RTP
Return to Player
Casino. The long-run percentage a game returns — typically 92–97%. House edge is 100% − RTP. Often displayed in-game for compliance reasons, which makes it something you can check is actually visible.
Bonus cost ratio
Bonus cost as a share of GGR. Operators watch this obsessively; it is frequently 20–40% and a constant tension between acquisition and finance.
Wagering requirement
How many times a bonus must be staked before it can be withdrawn — "30x". The single biggest source of player complaints and misunderstanding in the whole industry, and therefore a rich seam for UX work.
Game weighting
Which games count how much toward wagering. Slots often 100%, table games 10% or 0%. Almost never communicated clearly. Instrument whether players see it.

Players and value

FTD
First Time Depositor
A registered player who has made their first deposit. The central acquisition currency — affiliates are usually paid on it. "Reg-to-FTD" is the conversion rate everyone quotes.
Active / Actives
A player who wagered in the period. Usually "monthly actives" or "daily actives". Registration without activity is worthless.
ARPU / ARPPU
Average revenue per user; per paying user. In gambling, per active. In social gaming, ARPDAU — average revenue per daily active user — is the standard.
CPA / CAC
Cost per acquisition, usually per FTD. In competitive regulated markets this runs to the high hundreds of pounds, which is why a point of deposit conversion is worth so much.
LTV
Lifetime value, usually modelled on 6–12 month NGR. The LTV:CAC ratio is the business.
Churn / Dormancy
Churn is a defined period without activity — often 30, 60 or 90 days. Dormancy has regulatory meaning too: dormant accounts have handling rules.
VIP / High roller
A tiny population producing a very large share of revenue. Frequently 1% of players generating 40%+ of NGR. Any analysis that does not segment VIPs separately is misleading, and any VIP-affecting bug is an emergency.
Reactivation
Bringing a lapsed player back. Cheaper than acquisition and a standard CRM motion — and a good place to prove Fullstory's value, because reactivation landing experiences are usually terrible.

Operations

KYC
Know Your Customer. Identity, age and address verification. In Great Britain this must happen before a player can deposit or gamble, which puts it directly inside your conversion funnel — unlike most markets where it can be deferred.
AML / SoF / SoW
Anti-money-laundering; source of funds; source of wealth. Triggered at thresholds or by behaviour. Creates hard stops mid-journey that look like conversion failures in your funnel but are legally required. Always ask before you "fix" a drop-off.
PAM
Player Account Management platform — the system of record for accounts, wallet, bonuses and compliance. Everything else plugs into it.
PSP
Payment service provider. Operators run several and route between them; routing logic materially affects the deposit success rate you measure.
Chargeback
A disputed card payment. Costly and, at volume, threatens the operator's merchant relationships.
RG
Responsible gambling. Deposit limits, loss limits, time-outs, reality checks, self-exclusion. Both a licence condition and, increasingly, a product surface with real UX questions.
Self-exclusion / GAMSTOP
A player blocks themselves, at operator level or via the national scheme. Absolute and non-negotiable.
Affordability check
Assessing whether a player can sustain their losses. A major friction point in the GB market, often triggered mid-journey with significant conversion impact — and a place where better UX is genuinely in the player's interest.
Judgement

Some drop-offs must not be optimised away. A KYC hard stop, an affordability interruption, a self-exclusion check and a deposit limit prompt are all designed friction that the operator is legally required to impose. Your job on those journeys is to make them clearer, faster and less confusing — not to increase completion. Say this out loud, early and unprompted. It establishes that you understand the client's licence risk, and it is the fastest way to earn a compliance officer's trust.

The lifecycle, stage by stage

Every conversation with a gambling client maps to a stage of this journey. Knowing the typical failure mode and the typical benchmark at each stage lets you diagnose an account before you have opened their Fullstory.

  1. Acquisition Affiliate link, paid search, TV-driven brand search, or app store. Heavily affiliate-dependent in most markets. Instrument landing variant, affiliate ID, campaign, device, offer shown.
    Failure mode: the offer on the affiliate page does not match the offer on the landing page. Extremely common, entirely invisible without session data, and directly measurable.
  2. Registration Typically 3–5 steps: credentials, personal details, address, marketing preferences. Benchmark 40–65% completion once started; mobile web materially worse than app.
    Failure mode: address lookup failing, password rules revealed only on submit, date-of-birth pickers that are hostile on mobile, and mandatory marketing choices presented as blockers.
  3. Verification (KYC) Automated check against credit-reference and identity databases; manual document upload on failure. Benchmark 70–90% pass automatically; the manual fallback converts far worse.
    Failure mode: the player is dropped into a document upload with no explanation of why, no indication of how long it takes, and a camera flow that fails on older Android devices. This is routinely the biggest single loss in the whole funnel and it is rarely anybody's job.
  4. First deposit The moment the acquisition spend either pays back or does not. Benchmark 50–75% of verified players deposit; card approval rates in gambling are structurally lower than in retail because issuers decline gambling MCC transactions.
    Failure mode: a decline with no useful message. The player assumes the site is broken or that they have been refused, and leaves. A decline reason mapped to a helpful next step is one of the highest-return fixes available.
  5. First play Game launch or first bet. Benchmark should be well above 90% of depositors; anything lower is a technical fault, not a preference.
    Failure mode: game fails to load, bonus terms confuse the player into hesitating, or the player cannot find the game the promotion advertised.
  6. Early retention (days 1–30) The window that sets lifetime value. Benchmark D1 return 25–40%, D7 15–25%, D30 10–18% for real-money brands.
    Failure mode: no reason to return, bonus expiry not communicated, push notifications never opted into, and a second-session experience that treats a returning player like a stranger.
  7. Established play Habitual sessions. Value now depends on frequency and session quality. Failure mode: accumulated small frictions — slow lobby, failing search, repetitive re-authentication — that individually look trivial and collectively cause drift.
  8. Withdrawal The most emotionally charged journey on the site and the biggest driver of complaints and negative reviews. Failure mode: unexplained pending states, surprise verification requirements at the moment of withdrawal, and reverse-withdrawal patterns that players experience as manipulative. Treat withdrawal UX as a retention investment, because that is exactly what it is.
  9. VIP Manual account management, personal hosts, bespoke offers. Failure mode: the digital experience is unchanged while the service promise is premium. A VIP hitting a generic error is a phone call to the CEO.
  10. Responsible gambling intervention Limits, reality checks, time-outs, or a conversation. Failure mode: tools are buried, the language is punitive, and setting a limit feels like an accusation. Genuinely better design here helps players and reduces the operator's regulatory exposure at the same time — it is the rare case where the ethical and commercial arguments align completely.
  11. Lapse and reactivation Dormancy, then a campaign. Failure mode: the reactivation link deep-links to a page requiring re-verification, or to an offer the player is not eligible for. Measure the landing experience, not just the email open rate.
  12. Closure or self-exclusion Must be easy, fast and irreversible where required. Failure mode: a closure flow with more steps than registration. Regulators look at this specifically, and so should you — it is a five-minute audit that makes you look extremely serious.
Use it

Walk this lifecycle in the first discovery workshop and ask, at each stage, "what is your number, and who owns it?" You will discover two things in under an hour: which stages nobody measures, and which stages have no owner. Those two lists are your engagement plan, and you will have built it in front of the client rather than presenting it to them.

Things you must never recommend

  • Reducing friction in age or identity verification in a way that could let an unverified player gamble. Clarity yes; removal never.
  • Making responsible-gambling tools harder to find or use. Not even a small nudge. Not even "we moved it to a submenu for visual balance".
  • Targeting players by inferred vulnerability for any commercial purpose. If a client asks for a "high-loss-velocity" segment to send an offer to, decline and explain why.
  • Personalising promotions to self-excluded or time-out players. Ensure any segment you build feeds a suppression list, never an inclusion list, where RG status is involved.
  • Optimising the account-closure or self-exclusion flow for retention. Optimise it for speed. A regulator reading your deck should find nothing to object to.
  • Capturing anything from the KYC document journey beyond entry, outcome, reason code and duration.
Your line

"I optimise for comprehension and speed, not for completion, on any journey with a regulatory purpose. If a player is meant to stop and think, my job is to make sure they understand what they are being asked — not to get more of them through it." Learn it, mean it, and use it the first time it is relevant. It will define how the account treats you for the rest of the engagement.

Where regulation creates genuine opportunity

The constraint is also the opening. Compliance-mandated journeys are almost universally badly designed, because they were built to satisfy a legal requirement at minimum cost and nobody has revisited them since.

Make required friction legible

Players abandon KYC because nobody told them why it is happening or how long it takes. A single explanatory sentence and a progress indicator can lift completion substantially without weakening the check — the player is still verified, they just understand what is happening. This is the cleanest kind of win available on a gambling account.

Make RG tools genuinely usable

Deposit limits are typically buried in account settings behind punitive language. Presenting them neutrally and accessibly increases adoption, which reduces harm, reduces regulatory risk, and correlates with longer, healthier player lifetimes. You can argue this commercially and ethically at the same time, which is rare.

Prove compliance with evidence

Operators must show that required messaging was displayed. Fullstory can evidence that an RG message rendered, was in the viewport, and was interacted with — genuine, dated, session-level proof. Offer this to the compliance team early; it is a use case they did not know existed and it wins you an internal champion in an unexpected department.

Instrument the geolocation check

In US states, the geolocation check fails routinely — VPNs, poor GPS, desktop browsers, corporate networks. Each failure is a lost session and a support contact. Nobody measures it. Instrument attempt, outcome, reason and retry, and you will have found a meaningful loss inside a week.

Part III · Module 18

Six phases, ninety days

One framework, adapted per client. The sequence matters more than the timings: skipping discovery to get the tag live faster is the most common and most expensive mistake in this work, because every wrong decision made in week one is still being paid for in month six.

The six phases

Week 0–1 Phase 1 — Discover

Goal: know the business, the stack, the politics and the constraints before touching anything.

  • Commercial discovery: verticals, markets, brands, revenue mix, the two or three numbers the board watches
  • Technical discovery: deployment surfaces, tag manager, CSP, CMP, SPA or server-rendered, app estate, platform provider boundaries
  • Data discovery: warehouse, the player identifier, who owns BI, what already exists in GA4 or Amplitude
  • Stakeholder map: who decides, who blocks, who will champion, who was not told this was happening
  • Compliance discovery: DPO, data residency, retention appetite, sign-off route
  • Current-state pain: the top three things that frustrate the team today, in their words

Output: Discovery summary, stakeholder map, constraints register, draft success criteria.

Week 1–2 Phase 2 — Design

Goal: decide everything before a developer writes a line, so the build is a single pass.

  • Account structure: one org or several, brand and market property model, environment separation
  • Instrumentation spec: full event and property table with triggers, types and example values
  • Privacy design: the exclusion and masking list, walked page by page, signed by the DPO
  • Identity design: the hashed uid, where it is computed, how it joins to the warehouse
  • Measurement plan: which KPIs, which funnels, which dashboards, for which audience
  • Rollout plan: environments, phases, go-live criteria

Output: Instrumentation spec, Data Capture Statement, measurement plan, signed privacy design.

Week 2–4 Phase 3 — Deploy

Goal: capture running correctly and provably safely.

  • Snippet or SDK to staging; CSP and CMP configured
  • Identity wiring and verification against the warehouse key
  • SPA page rules; element naming on key controls
  • Custom events implemented, in priority order: money flows first, engagement second, content last
  • Privacy audit in staging, then production within 24 hours of go-live — screenshotted for the file
  • Volume reconciliation against the client's own analytics

Output: Capture live, QA report, privacy audit evidence pack.

Week 4–6 Phase 4 — Validate

Goal: prove the data is trustworthy before anyone makes a decision on it.

  • Build the day-one segment library and the four core funnels
  • Reconcile: Fullstory deposit success versus the payments team's own figure. Explain every gap or you will be ambushed later
  • Build the audience dashboards; agree definitions in writing
  • Configure the first three alerts and tune thresholds
  • Deliver the first finding. Non-negotiable. Error clicks are the reliable source

Output: Reconciliation note, segment and funnel library, dashboards, first quantified finding.

Week 5–9 Phase 5 — Enable

Goal: make it theirs. This is the phase that determines renewal.

  • Role-based training: separate sessions for analysts, product, engineering, support, executives
  • A one-page quick-reference per role, in their language, not Fullstory's
  • Integrations that create habit: support ticket replay links, Jira, experimentation variants
  • Office hours weekly for four weeks — drop-in, no agenda. Catches every silent misunderstanding
  • Name and equip an internal champion per team

Output: Trained teams, quick-reference cards, live integrations, named champions.

Week 8–12+ Phase 6 — Embed

Goal: turn a tool into a working rhythm.

  • A recurring insight cadence — fortnightly findings, monthly review, quarterly business review
  • Fullstory evidence made mandatory in the client's own bug and discovery templates
  • Data Direct to the warehouse and the first NGR-joined analysis
  • Governance: naming conventions, an owner per dashboard, a quarterly access and masking review
  • An opportunity backlog, quantified and prioritised, that the client's roadmap actually draws from

Output: Operating rhythm, warehouse join, governance model, quantified backlog.

Rule

A finding in week four or the account never recovers. Clients judge the tool by whether it told them something they did not know, quickly. Hold a known easy win in reserve from the first day of capture — an error click cluster, a dead-click promotion, a mobile rage-click hotspot — and deliver it the moment the data is credible enough to defend.

Shape

Sportsbook plus casino, 3–8 brands, in-house React front end, own platform or deep platform partnership, Snowflake, a real data team. Hundreds of people could use the tool.

What is hard

Politics, not technology. Every brand has its own product owner and its own view. Compliance sign-off is a real gate with a real queue. Nothing ships without going through change management.

Emphasis

Spend double the normal time in Discover and Design. Get the account structure and the brand property model right — migrating later is brutal. Win the BI lead early; they decide whether this becomes strategic or stays a UX toy.

Timeline

12–16 weeks to Embed. Do not promise faster; you will miss it and spend the rest of the engagement apologising.

First win

A cross-brand comparison nobody has ever been able to run — the same funnel, five brands, side by side. It is politically explosive and commercially irresistible.

Risk

Becoming the tool of one department. Insist on a cross-functional steering group from week one, or you will be renewed by one budget holder and cancelled by their successor.

Shape

Casino only, one or two markets, small team, everything outsourced. The client owns the CMS pages and the brand skin; the provider owns registration, cashier and the game launcher.

What is hard

You cannot deploy where the money is. The provider has no contractual incentive to help and will quote for the work.

Emphasis

Establish the deployment boundary in the first call. Then maximise what GTM can reach, and instrument the edges of the black box: every entry into the cashier and every return from it, with the outcome the page displays. Build the business case for provider cooperation with the data you can get.

4–6 weeks to Validate, then a long tail waiting on the provider.

Lobby and game discovery — entirely within the client's control, immediately actionable, and usually badly broken. Zero-result searches and dead promotional tiles are reliable finds.

Scope frustration. Be explicit and repeated about what is out of reach, in writing, or you will be blamed for the provider's boundary.

Mobile instrumentation ships with app releases, so you get one shot per cycle. Webview and native session linkage is fiddly. Privacy defaults on mobile are the opposite of web and must be audited carefully.

Front-load the mobile event schema and get it fully reviewed — you cannot iterate weekly. Instrument betslip and in-play latency above everything else. Plan capture volume around the fixture calendar.

Betslip abandonment on mobile web, delivered while the app work is in the release queue. Also: price-change rejection rate, which almost no sportsbook measures from the player's side.

Quota burn on a big fixture weekend. Configure sampling and alerts before the first major event, not after.

The game itself is canvas or engine-rendered, so replay shows almost nothing of gameplay. The team has a sophisticated event pipeline already and will ask what Fullstory adds.

Emphasis

Position Fullstory around the non-game surfaces — onboarding, the store, offers, settings, support — which is where monetisation and churn actually break and where their existing telemetry is thinnest. Focus on first-session experience and the IAP funnel.

3–5 weeks; these teams move fast and have their own instrumentation habits.

First win

First-session drop-off at a specific tutorial step, with replays showing exactly what confused people. Their aggregate funnel already shows the drop; nobody has been able to see the cause.

Being treated as a duplicate of their existing analytics. Draw the line hard: aggregate tools tell them where, this tells them why.

Shape

One brand, one market, 20–80 people. Probably a platform partner. The CEO is in the kick-off call and will stay in every call.

What is hard

No dedicated analyst, no BI team, no spare dev capacity. Enthusiasm is high and follow-through is thin.

Emphasis

Ruthless minimum viable instrumentation — registration, KYC, deposit, game launch, and nothing else until those are working. Pre-build everything: segments, funnels, dashboards. Assume they will not build their own.

3–4 weeks to first value. Speed is the whole proposition here.

First win

Registration and KYC funnel drop-off with named causes. For a challenger, every lost registration is money they cannot spare and the CEO will act on it that week.

Usage collapses the moment you stop pushing. Build a lightweight recurring rhythm — one 30-minute fortnightly session — and defend it.

Multi-tenancy. One codebase, many skins, many operators, and data-segregation obligations between them. An operator must never see another operator's sessions.

Emphasis

Tenant identification as a first-class session property from day one, and an access model that enforces separation. Two distinct measurement programmes: back-office efficiency for operator staff, and conversion for end players.

8–12 weeks; the access and segregation design is the long pole.

First win

Back-office usability. Operator staff use these tools all day, they are usually dreadful, and improvements are immediately felt by the client's own paying customers — which is a commercial story, not just a UX one.

A data-segregation mistake is an existential incident for them. Design the access model before capture goes live, and have it reviewed.

Principles

  1. Never demo on sample data Use their site, their players, their last release. The first time they see their own broken thing, the room changes.

Part IV · Method

The finding is not the deliverable. The change is.

Everything before this module teaches you to find things. This one is about what happens next — because at a conversion consultancy the research instrument is not the product. The tested, measured, shipped change is. Fullstory sits at both ends of that loop: it generates the hypothesis and it explains the result.

Where Fullstory sits in the cycle

  1. Research Quantify where the loss is and watch why it happens. Fullstory Funnels, frustration signals, journeys, replay. This is where most of this platform lives.
  2. Hypothesise Convert the observation into a falsifiable claim with a named mechanism.
  3. Prioritise Rank against effort, confidence and reach so the roadmap is defensible rather than loudest-voice-wins.
  4. Design and build The variant. Not your job, but your spec decides whether it can be measured.
  5. Run With a pre-registered metric, a pre-calculated sample size and a fixed end date. Fullstory Variant as a session property, from day one.
  6. Analyse Beyond the primary metric, to the money. Fullstory Watch the losing variant — the thing no test platform can do.
  7. Learn Record the result whether it won or lost, and feed it back into research. The archive of losses is the most undervalued asset any CRO team owns.
The pitch

"Your test platform tells you which variant won. It cannot tell you why the loser lost, and it cannot tell you what to test next. That is the half we do."

Writing a hypothesis that can fail

A hypothesis that cannot be wrong is a plan, not a hypothesis. The shape that works:

BECAUSE  [evidence — quantified, with the source]
WE BELIEVE THAT  [specific change]
WILL CAUSE  [primary metric] to move [direction] by [at least MDE]
BECAUSE  [mechanism — why the change causes the effect]
WE WILL KNOW WE ARE WRONG IF  [what a null or negative result looks like]

Worked example
  BECAUSE  38% of failed first deposits show a generic "unable to
           process" message and 61% of those players never retry
           (4,100 sessions/month, Fullstory deposit funnel, Aug)
  WE BELIEVE THAT  mapping the top six decline reasons to a specific
           next step, with an alternative method offered inline
  WILL CAUSE  retry rate after decline to rise from 44% to at least 52%
  BECAUSE  players currently cannot tell whether the fault is theirs,
           ours or their bank, so they assume refusal and leave
  WE WILL KNOW WE ARE WRONG IF  retry rate moves less than 5 points,
           or retries rise but successful deposits do not

The last line is the one people skip and the one that matters. Without it, a flat result gets rationalised into a partial win and the team learns nothing.

Mechanism

Insist on the mechanism clause. "Because players will like it more" is not a mechanism. "Because the current copy does not distinguish a bank refusal from a typo" is. A hypothesis with a real mechanism produces a useful lesson even when it loses, because you learn the mechanism was wrong. One without a mechanism produces nothing either way.

Named public frameworks — ICE, PIE and PXL are the common ones. They matter less for their arithmetic than for forcing the conversation into the open. Whichever you use, apply it consistently and publish the scores.

Sample size: the maths that decides whether a test is worth running

Most tests that "fail to reach significance" were never capable of reaching it. Run the numbers before the ticket is written, not after the result disappoints.

A standard approximation for a two-variant test at 95% confidence and 80% power:

n per variant  =  16 × p(1−p) / δ²

  p  baseline conversion rate, as a proportion
  δ  absolute change you want to detect
     ( = p × relative MDE, so a 10% relative lift on a 30%
       baseline is δ = 0.03 )

Detecting a 5% relative improvement on deposit success at a 90% baseline takes under 3,000 sessions per variant. Detecting the same relative improvement at the top of the acquisition funnel takes over 120,000.

This is why so much gambling CRO work quietly concentrates on the cashier: it is where the traffic is dense, the baseline is high, the money is immediate — and the tests actually conclude.

The VIP problem

The population that produces most of the revenue is far too small to test on. A brand with a few hundred VIPs cannot run a VIP-only experiment to any useful precision, ever. What you can do instead: run the test on the whole population, then use Fullstory to watch how VIPs experienced the variant, and treat that as qualitative evidence alongside the quantitative result on everyone else. Say this out loud when someone proposes a VIP test, before three weeks are spent on it.

Test duration and the gambling calendar

  • Always run whole weeks. Gambling traffic has a violent weekly shape — weekends, evenings, fixture days. Stopping mid-week means your variant saw a different week than your control.
  • Two full weeks is the practical minimum, even if the sample arrives sooner, so a weekly cycle is covered twice.
  • Check the fixture calendar before you start. A Grand National, a World Cup match or a large jackpot can multiply traffic and change its composition completely. A test that spans one and not the other is comparing two different populations.
  • Watch for promotional overlap. A CRM campaign launched mid-test is a confound nobody will tell you about. Ask the retention team for their calendar and put it next to yours.
  • Do not stop early because it looks good. Peeking at a fixed-horizon test inflates false positives substantially. If the client insists on monitoring, agree in advance that only the pre-set end date can stop it — or use a platform with proper sequential testing and let it do the correction.

Validity checks, in the order you should run them

  1. Sample Ratio Mismatch Did the split land where you set it? A 50/50 test that delivers 48/52 on large numbers is usually a bug — a redirect, a caching layer, a bot filter applied unevenly, or the tag firing late on one variant. SRM invalidates the test entirely. Check it first, every time, and if it fails, stop and find the cause rather than reasoning about the result.
  2. Instrumentation parity Did both variants fire the same events? Use Fullstory to confirm that the variant's own tracking works — a variant that under-reports its own success is a classic and embarrassing false negative.
  3. Novelty and primacy Returning players react to change as change. A lift in week one that decays in week two is novelty; a dip that recovers is primacy. Segment new versus returning and look at both separately.
  4. Segment consistency If the overall result is flat but mobile won heavily and desktop lost heavily, the headline is hiding two findings. Look before you conclude nothing happened.
  5. Downstream effects The tested step is not the business. A variant that increases cashier opens but not successful deposits has moved a number, not the money.
Honesty

Segment analysis after the fact is exploratory, not confirmatory. Slice enough ways and something will look significant by chance. Use post-hoc segments to generate the next hypothesis, never to rescue a flat result. Say "this is exploratory" in the deck, in writing — it is the difference between an analyst who is trusted with the numbers and one who is managed.

What Fullstory does that the test platform cannot

Watch the loser

Push the variant into Fullstory as a session property, then watch sessions from the losing variant that reached the tested step and failed. Nine times out of ten there is a visible reason — a control that moved under the thumb, a message that reads as an error, a layout that pushed the action below the keyboard. The test platform reports the loss; only replay explains it.

Explain a flat result

A null result usually means one of three things: nobody noticed the change, they noticed and did not care, or the change broke for a subset. Those are completely different lessons and they look identical in aggregate data. Frustration signals and replay separate them in an afternoon.

Catch a broken variant

Filter JavaScript errors and error clicks by variant. A variant that throws on one browser will drag its numbers down for reasons that have nothing to do with the hypothesis, and the test platform has no idea.

Find the next test

Segment comparison between converters and non-converters within the winning variant tells you what is still failing after the fix. The best source of the next hypothesis is almost always the residue of the last one.

Things you cannot test on a gambling account

  • Anything that weakens age or identity verification. Not even as a variant, not even briefly.
  • Responsible-gambling tool prominence, in the direction of less. You may test clearer; you may not test quieter.
  • Mandated messaging presence. Wording changes may be testable with compliance sign-off; presence is not.
  • Affordability and RG interruptions, optimised for pass rate. Comprehension and speed only, with the objective stated as such in the test document.
  • Anything that differentiates by inferred vulnerability. Including, quietly, a targeting rule that happens to correlate with it.

Put these in the test plan template as a standing exclusions list, so the question is answered before someone proposes one in a workshop. It also demonstrates to a compliance officer that the programme has guardrails designed in rather than applied afterwards.

Nine patterns. Every KPI is one of them.

There are only nine shapes of metric you will ever build in Fullstory. Learn the nine and the encyclopedia stops being a reference you look things up in and becomes a list you can construct from memory. Each KPI in the next module is tagged with its pattern.

The key

Fullstory's metric builder does not divide one arbitrary segment by another. A two-step funnel is how you get a rate. Step 1 is your denominator, step 2 is your numerator, and the funnel's conversion figure is the KPI. Once that clicks, most of this module is mechanical.

The nine patterns

funnel  Funnel conversion — an ordered rate

Use when the KPI is "X of the people who did A went on to do B", and order matters.

  1. Decide the scope. Session scope for anything that happens in one visit (deposit, betslip). User scope for anything spanning visits (reg-to-FTD, retention, verified-to-deposit).
  2. Add one funnel step per real stage. Resist compressing — a five-step registration needs five steps or you cannot see which one breaks.
  3. Set the conversion window deliberately: same session, 24 hours, 7 days, 30 days. This choice changes the number more than anything else and is the first thing BI will challenge.
  4. Save it as a metric and chart the step-to-step conversion over time.
  5. Apply a segment overlay. An unsegmented funnel on a multi-brand operator is close to meaningless.

Reading it: the step with the biggest percentage drop is not always the biggest opportunity — multiply each drop by the volume reaching that step and rank by absolute players lost.

rate  Simple rate — share of a population

Use when the KPI is "X% of sessions/users had this characteristic", with no ordering.

  1. Build the denominator segment first and write down exactly what it includes. Most wrong numbers are wrong denominators.
  2. Build the numerator segment as the denominator plus the condition.
  3. Express as a two-step funnel (denominator → numerator) to get the percentage natively, or chart both counts and divide on the card.
  4. Chart daily for high-volume KPIs, weekly for anything user-scope.

Trap: a denominator of "all sessions" is almost always wrong. Saved-method adoption measured against all deposits includes first deposits where nothing could have been saved.

seg  Segment size — a population over time

Use when the KPI is a count or a share of a fixed base: monthly actives, churned players, registered-but-never-verified.

  1. Build the segment, usually user scope, using did / did not / sequence / count conditions.
  2. The did not operator is the workhorse here — nearly every valuable gambling segment is a negative.
  3. Chart unique users, and separately as a share of the relevant base.
  4. Save it: these segments double as CRM audiences and as replay entry points.

Craft: name it so a stranger can use it. [Cashier] 3+ deposit attempts — session, not test 4.

time  Duration — how long something took

Use when the KPI is a time: time to deposit, time to verification, time in betslip.

  1. Capture the elapsed time as a numeric property on the completing event — secondsElapsed, secondsToOutcome. Do not try to derive it from event timestamps after the fact; timezone and batching noise will defeat you.
  2. Metric → median of that property. Never the mean; a handful of abandoned tabs will destroy a mean.
  3. Always chart the 90th percentile alongside the median. The tail is the finding.
  4. Filter to successful outcomes only where a failure would contaminate the duration.

Say this: "Your median is 110 seconds, which looks fine. Your P90 is nine minutes, which is a quarter of a million players a year having a bad time."

dist  Distribution — a breakdown by property

Use when the KPI is a mix or a ranking: payment method mix, decline reasons, tile clicks by position.

  1. Metric → event count, with a breakdown by property.
  2. For a mix that changes, chart as a stacked area over 90 days rather than today's pie.
  3. For a ranking, sort descending and take the top eight — nobody acts on a list of forty.
  4. Where position or exposure biases the ranking (lobby tiles, method ordering), normalise before ranking or you will simply re-measure the layout.

Trap: high-cardinality properties make this useless. Bucket numerics at instrumentation time; a breakdown by raw stake amount is a list of ten thousand rows.

signal  Derived signal — frustration and errors

Use when the KPI comes from Fullstory's own derived signals: rage, dead and error clicks, JS errors, thrashed cursor.

  1. Suppress the false positives first. Steppers, quick-stake chips and spin buttons generate legitimate repeat clicks. Do this before you report anything.
  2. Session segment: signal present, optionally scoped to an element or page group.
  3. Metric → share of sessions, not raw count. Counts just rank pages by traffic.
  4. Group by signature or element and rank by distinct sessions affected.
  5. Quantify: build a matched control that reached the same step without the signal and compare downstream conversion.

Always pair with a number. A signal without a value attached is the thing a sceptical Head of Digital will use to dismiss the whole tool.

perf  Performance and journey analysis

Use when the KPI comes from autocaptured performance data or from path analysis: LCP, INP, CLS, scroll depth, navigation depth, contact drivers.

  1. Define page groups first. Per-URL performance on a gambling site with thousands of event pages is unreadable.
  2. Report the 75th percentile for web vitals; the median flatters and the mean is meaningless.
  3. Split by device class — mid-range Android is the real test, not the analyst's iPhone.
  4. For journeys, run them backwards from a bad outcome. Forward paths from the homepage are interesting; backward paths from a support contact are actionable.
  5. Convert into content terms before presenting: rows, screens, clicks — never bare percentages.
wh  Warehouse-joined — behaviour meets money

Use when the KPI needs revenue, wagering or settlement data Fullstory cannot see: NGR per active, hold %, LTV, wagering completion, spins per session.

  1. Confirm the hashed uid genuinely joins to the warehouse player key. Test it on one real record before promising anything.
  2. Define the behavioural cohort in Fullstory — that is your half of the work.
  3. Export via Data Direct.
  4. Have the client's BI team return the financial figure per cohort. Their query, their name on it.
  5. Present the joined result together, with both teams credited.

Rule: never build the pipeline alone and hand it over. A warehouse join built by an agency is a join nobody queries after the engagement ends.

ext  External system — Fullstory supplies context, not the number

Use when the metric lives in another tool entirely: CPA, chargebacks, crash-free rate, NPS, handle time, accessibility audits.

  1. Get the figure from its system of record, in writing, with the definition attached.
  2. Use Fullstory for the explanation: the sessions behind the disputed deposits, the journeys behind the detractor scores, the seconds before the crash.
  3. Where possible, pass the Fullstory session URL into the other tool so the join is automatic rather than manual.
  4. Be explicit in every deliverable about which half came from where.

Credibility: overclaiming what Fullstory measures is the fastest way to lose a technical stakeholder. "That comes from your payments platform; what I can add is why it happened" is a stronger sentence than any number.

Before you build anything

  1. Write the definition down first Scope, denominator, numerator, window, exclusions. One sentence. If you cannot write it, you cannot defend it when BI asks.
  2. Check the instrumentation exists Every recipe in the encyclopedia names its prerequisite. A KPI whose events are not yet firing is an instrumentation ticket, not a dashboard card.
  3. Decide the four cuts For a gambling client the default set is market, brand, device and new-versus-returning. Build the metric so those overlays are one click away.
  4. Build the inverse segment too For every conversion metric, save the failure population. That is where the replays are, and replays are where the finding is.
  5. Name it for a stranger Area, metric, scope. The segment and metric lists become shared infrastructure in an account with forty users.
  6. Reconcile before you publish Compare against the client's own number for the same window and explain the gap in writing. Do this once per metric, early, and you will never be ambushed in a meeting.
Remember

The exact menu paths, metric types and builder options move between Fullstory releases. The patterns above are stable because they follow from how the data model works. Check the current UI for the specific control before you write a step-by-step guide for a client.

The eight defects

All eight are deliberately planted. Do not read the list before you hunt — try to find them from the data first, then check yourself here.

Reveal the answers (hunt first)
  1. A dead promotional banner. Styled exactly like a button, does nothing at all. Find it in dead clicks.
  2. A game tile that throws. One tile raises an uncaught exception on click. Find it in error clicks and read the stack in the console tab.
  3. A deposit button with no feedback. Takes four seconds with no spinner, so people hammer it. Find it in rage clicks, then confirm the wait in the network tab.
  4. A card field that is not excluded. Fully captured, in plain view in replay. This is the one that should genuinely alarm you.
  5. A validation rule revealed only on submit. Password rules are never shown until the form is rejected. Find it in form abandonment on step 2.
  6. A silent deposit failure. One in three attempts fails and shows a generic message with no next step. Find it in the deposit funnel and the decline reason property.
  7. A lobby search that returns nothing for a real game. A title that exists in the grid is missing from the search index. Find it in zero-result searches.
  8. An RG link buried in the footer. Four clicks deep from the cashier, where people actually are. Find it with journey analysis, then measure the click depth.

The exercises

  1. Prove the capture model to yourself Launch the fake game. Watch the replay. The canvas is blank — exactly as it will be on every casino client you ever work on. Now open the element inspector mid-replay and read the selector of the tile you clicked. That contrast, felt once, is worth more than the paragraph explaining it.
  2. Break privacy, then fix it Type a fake card number into the cashier. Watch the replay and see it captured in full. Sit with that for a second. Then add class="fs-exclude" to the card field container, reload, repeat, and confirm the striped rectangle. Finally, note what you lost: excluding the whole cashier block also loses the confirm click. Move the exclusion to the fields only and get both.
  3. Name an element and watch search change Add data-fs-element="Cashier / Deposit Confirm" to the deposit button. Reload, click it, then search for it by that name rather than by its text. Then mask the surrounding block and try to find it by text — you cannot, because masked text is never collected. This is the exercise that makes element naming stop feeling optional.
  4. Fire your first custom event Add a trackEvent call to the deposit button with a bucketed amount, a payment method and an attempt number. Search for it. Then deliberately send depositAmount as a raw number instead of a bucket, generate twenty deposits at different values, and look at what the property breakdown becomes. You will not need to be told about cardinality again.
  5. Build a funnel and read a real drop Cashier Opened → Deposit Attempted → Deposit Outcome success. The sandbox fails one deposit in three. Confirm the funnel shows it, then click through to the failing sessions and watch what the player is told. Write the better error message.
  6. Rank the frustration signals honestly Look at rage clicks. The stake stepper will be near the top and it means nothing. Suppress it, re-run, and see what surfaces underneath. This is the single most transferable habit in the whole platform.
  7. Quantify one defect end to end Take the dead banner. Segment sessions that clicked it, build a matched segment that reached the same page and did not, compare how many went on to a successful deposit. Write the one-pager from the templates module using a made-up ARPU. The point is the shape of the argument, not the number.
  8. Deliberately misidentify yourself Call setIdentity with one uid, then call it again with a different one in the same session, and see what happens. Identity cannot be reassigned once set — discovering that here, on a throwaway account, is considerably better than discovering it on a client's production traffic in week three.
  9. Test the consent path Initialise with capture off, add a fake consent button that starts capture, and confirm nothing is recorded before it is pressed. Then call shutdown and confirm capture stops. Most clients never test the withdrawal path; you will have, and you will know how long it takes.
  10. Watch yourself cold Come back the next day and watch your own sessions without remembering what you did. Try to reconstruct your intent purely from the replay. That gap — between what you meant and what the data shows — is exactly the gap your clients will be sitting in, and feeling it once makes you far more careful about the conclusions you draw from five sessions.

What changes when you run it locally

Works Everything structural

  • Every module and every word of content
  • Global search across lessons, KPIs, requirements and glossary
  • All filters, the drill deck and scoring
  • The onboarding plan generator, including copy-to-clipboard
  • Light and dark themes, and the keyboard shortcuts
  • Your progress, notes and quiz score — saved in that browser

Differs Three things

  • The scenario coach is hidden. It needs the hosted runtime to reach Claude, so the local copy disables it rather than showing a broken button.
  • Progress is per-browser, not per-person. The hosted version syncs your notes and ticks across devices; the local copy stores them in that one browser's storage. Use Chrome on the laptop and Edge on the desktop and you will have two separate sets of notes.
  • Fonts need the internet on first load. Offline, the page falls back to system fonts. It reads perfectly well, it just looks plainer.
Suggestion

Use the hosted version for your notes, because they follow you between machines and survive a laptop rebuild. Keep the local copy for client sites — guest wifi in gambling offices is frequently locked down, and having the KPI encyclopedia and the requirements library available offline in a meeting is worth the duplication.

Editing it

It is plain HTML, CSS and JavaScript with no build step, so you can change it in Notepad, VS Code or anything else. The three places worth knowing:

Add a KPI
Add an entry to the array in data-kpi.js (name, category, formula, range, capture note), then add a matching entry keyed by the same name in data-kpi-build.js. The category chips and counts update themselves.
Add or reword a requirement
Add an object to the array in data-req.js. Keep the theme value to one of the existing filter names or add a new chip in index.html.
Change the plan generator's judgement
BUILDER.run() at the bottom of data-req.js. The risk list is a series of plain if statements — one per client attribute. Rewrite them as your own experience accumulates; the weightings in there are a starting position, not a finding.
Add a module
Create a file in src/ containing a <section class="view" id="v-yourid" data-part="…" data-nav="…">, add its filename to ORDER in build.py, and rebuild. Numbering, navigation, search and the progress counter all follow automatically — do not put a number in data-nav.
Note

Edit the local copy and the hosted version does not change, and vice versa — they are separate. Commit your changes, and index.html can be republished to the same hosted link whenever you want the two back in step.
