1. Kick-off agenda

Ninety minutes, the whole room, before any access is granted. The purpose is not to present — it is to surface the constraints that will otherwise ambush you in week six.

FULLSTORY ONBOARDING — KICK-OFF
[Client] · [Date] · 90 minutes

ATTENDEES REQUIRED
  Exec sponsor · Product owner (cashier) · Front-end lead
  BI / data lead · DPO or compliance · Marketing/acquisition
  Platform provider account manager (if white label)

1. Outcomes (10 min)
   What must be true in 90 days for this to be a success?
   Whose KPI moves? Who signs off a fix once we find one?

2. Commercial picture (15 min)
   Verticals, markets, brands, revenue mix
   The two or three numbers the board watches weekly
   Current reg-to-FTD and deposit success rate
   Cost per FTD

3. Technical reality (25 min)
   Which pages can you deploy JavaScript to WITHOUT a third party?
   SPA or server-rendered? Router? Tag manager? Who approves publishes?
   CSP change process · Consent platform and category
   Native apps: platforms, release cadence, webview surfaces
   Who owns the cashier, registration and game launcher?

4. Data (15 min)
   Warehouse and owner
   The identifier that links a web session to a player record
   Existing tracking plan · Existing analytics and who trusts it

5. Privacy and compliance (15 min)
   DPO sign-off route and timeline
   Data residency constraints from any licence held
   Retention period the client would defend to a regulator
   JOURNEYS WITH MANDATED FRICTION THAT MUST NOT BE
   OPTIMISED FOR COMPLETION — list them explicitly

6. Next steps (10 min)
   Named owner per workstream · Date for instrumentation spec
   Date for privacy sign-off · Date of first finding

CLOSING STATEMENT (say this out loud)
  "On any journey with a regulatory purpose I optimise for
   comprehension and speed, not completion. If a player is meant
   to stop and think, my job is to make sure they understand what
   they are being asked — not to get more of them through it."

2. Instrumentation specification

The single most important document you will write. A developer must be able to implement from it without asking you one question. One row per event; do not ship a spec that lists only event names.

INSTRUMENTATION SPECIFICATION — [Client] — v[n] — [Date]

CONVENTIONS
  Event names   Title Case, describing what happened
  Properties    camelCase
  Numerics      Bucketed. Never send raw amounts, stakes or balances.
  Join keys     Every commercially significant event carries an ID
                the warehouse also holds (depositId, betId).
  Never send    Names, emails, card data, document numbers, DOB,
                addresses, free text typed by the player, RG risk
                scores or vulnerability classifications.

IDENTITY
  Call          FS('setIdentity', { uid, properties })
  uid           Salted server-side hash of the internal player ID
  Salt held by  [Client], never by [Agency]
  Fires on      Login AND persistent-session restore
  WARNING       Identity cannot be changed once assigned. Sign off
                the key with the BI lead before a line is written.

EVENT: [Deposit Outcome]
  Trigger       [Fires when the PSP response is received and the
                 result is rendered to the player]
  Page/surface  [Cashier — all entry points]
  Server-side?  [Yes — authoritative outcome also sent via Events API]
  Property           Type     Allowed values / example      Feeds KPI
  outcome            string   success | failed | pending    Deposit success rate
  declineReason      string   [mapped list — attach]        Decline league table
  providerCode       string   raw PSP code                  Issuer analysis
  provider           string   [Trustly|Worldpay|…]          Provider comparison
  paymentMethod      string   [card|applepay|paypal|…]      Method mix
  depositAmountBucket string  0-9 | 10-24 | 25-49 | …       Value distribution
  attemptNumber      integer  1,2,3…                        Friction proxy
  secondsElapsed     integer  seconds since Cashier Opened  Time to deposit
  threeDsUsed        boolean  true|false                    3DS challenge rate
  threeDsOutcome     string   completed|abandoned|failed    3DS completion
  isFirstDeposit     boolean  true|false                    FTD analysis
  depositId          string   join key to warehouse         NGR attribution

[repeat per event — see the taxonomy module for the full list]

ELEMENT NAMING
  Pattern       data-fs-element="Area / Component / Action"
  Required on   Cashier confirm, method tiles, registration step CTAs,
                betslip place-bet, game tiles, RG tool entry points
  Why           Locale-independent, survives CSS-in-JS rebuilds, and
                masked regions can only be searched by selector.

ACCEPTANCE CRITERIA
  [ ] Every event fires once and only once per real occurrence
  [ ] Property types match this spec exactly
  [ ] No raw monetary values anywhere in the payload
  [ ] Verified in staging with a replay walkthrough
  [ ] Volume reconciled against [client analytics] within 15%

3. Data Capture Statement

One page. Closes the DPO conversation permanently and is the most reused artefact you will build. Re-issue it after every significant redesign.

DATA CAPTURE STATEMENT — [Client] — [Date] — v[n]

PURPOSE
  Behavioural analytics and session replay to diagnose and improve
  the customer experience. Lawful basis: [legitimate interests /
  consent] as assessed by [Client] in [DPIA reference].

ROLES
  Controller [Client] · Processor Fullstory · DPA [reference/date]
  Data residency [region] · Retention [n] months

WHAT IS CAPTURED
  Page structure and its changes; clicks, taps, scrolls, navigation;
  form interaction (which field, how long, whether completed);
  console and JavaScript errors; network request timing;
  custom events listed in the instrumentation specification.

WHAT IS NOT CAPTURED
  Values typed into inputs (private by default and not overridden).
  Excluded entirely (fs-exclude):
    card number, expiry, CVV, cardholder name; bank details;
    national insurance / tax IDs; passport and licence numbers and
    images; source-of-funds documents; full DOB; full address;
    passwords, security answers, one-time codes;
    free text typed by the player into support chat.
  Masked (fs-mask — structure kept, content obfuscated):
    player name and username; account, bonus and withdrawable
    balances; transaction and bet history amounts; email address
    where rendered; partial card display; player-set limit values.
  NEVER SENT AS PROPERTIES
    Markers-of-harm scores, risk bands, vulnerability
    classifications or intervention history.

RESPONSIBLE GAMBLING DATA
  Interaction with RG tools is captured (that a tool was opened,
  what action was taken). Inferred risk or harm is not captured and
  no segment is built to target players by inferred vulnerability.

ACCESS
  Replay access restricted to [named group, n people].
  Reviewed quarterly. Last review [date].

DELETION
  Player erasure executed via the Fullstory server-side Users API.
  Owner [name, role]. SLA [n] days from DSAR receipt.
  Runbook [link]. Last tested [date].

ASSURANCE
  Masking verified in production on [date] by [name].
  Evidence pack [link]. Next audit due [date].

Signed  [Client DPO] ............  [Agency lead] ............

4. Metric definitions & reconciliation note

Produce this in week five, before anyone makes a decision on the data. It is the document that stops the "your number is wrong" conversation from ever happening.

METRIC DEFINITIONS & RECONCILIATION — [Client] — [Date]

METRIC  [Deposit success rate]
  Fullstory definition
    Scope        Session
    Numerator    Deposit Outcome where outcome = success
    Denominator  Deposit Attempted
    Window       Same session
    Exclusions   Internal IP ranges, known bots, [staging traffic]
  [Client BI] definition
    Numerator    [settled deposits in ledger]
    Denominator  [transactions submitted to PSP]
    Window       [calendar day]
    Exclusions   [reversals, test accounts]
  Observed on [date], same 24h window
    Fullstory [68.2%]   BI [61.4%]   Gap [6.8pp]
  Gap explained by
    1. [BI counts PSP-submitted only; Fullstory counts player
       attempts including those failing before submission — 4.1pp]
    2. [Consent-suppressed sessions absent from Fullstory — 1.9pp]
    3. [Residual, unexplained — 0.8pp, accepted]
  AGREED
    For [UX diagnosis] use the Fullstory definition.
    For [financial reporting] use the BI definition.
    Neither is wrong. They answer different questions.

  Fullstory publishes guidance on why these differ:
  help.fullstory.com — "Why do I see different numbers in
  Fullstory and a third-party tool?"

Signed  [BI lead] ............  [Agency lead] ............

6. Provider SLA report (casino)

Commercial leverage disguised as a technical report. Operators pay revenue share to game providers with almost no objective quality data; you are supplying it.

GAME PROVIDER QUALITY REPORT — [Client] — [Month]

METHOD
  Client-side measurement of game launch outcomes captured in
  Fullstory. Launch = Game Launched event. Success = Game Load
  Outcome with outcome=success. Time to playable measured to the
  provider's ready callback where available, otherwise to iframe
  load (noted per provider).

  Provider    Launches  Success  P50 load  P90 load  <60s exit
  [Provider A]  412,880   99.1%     2.4s      5.1s      18%
  [Provider B]  318,440   96.3%     4.9s     14.2s      34%
  [Provider C]  ...

BY DEVICE — [Provider B]
  iOS            98.1%   ·  Android (flagship)  97.4%
  Android (mid)  91.2%   ·  Desktop             99.0%

TOP FAILING TITLES — [Provider B]
  [Game]  [failure rate]  [top error code]  [sessions affected]

COMMERCIAL CONTEXT
  [Provider B] carries [x%] of launches and [y%] of revenue at a
  failure rate [z] times the portfolio average. Estimated lost
  sessions [n]/month; estimated NGR impact [range], using
  [Client]'s NGR-per-active figure of [£].

ASKS OF THE PROVIDER
  1. [Ready callback exposed so time-to-playable is measurable]
  2. [Mid-range Android performance plan with dates]
  3. [Error code documentation]

NOTE  Measured from the player's browser, so it includes network
and device conditions the provider does not control. It is
therefore a measure of PLAYER EXPERIENCE, not of provider uptime.
Both matter; be explicit about which this is.

APPENDIX  Metric definitions · Data Capture Statement · Evidence
Habit

Fill these in during the engagement, not at the end of it. The kick-off agenda, instrumentation spec and Data Capture Statement are week-one-and-two documents; the reconciliation note is week five; the opportunity one-pager is every fortnight. A QBR assembled from documents that already exist takes an hour. One assembled from memory takes two days and is worse.
